# Operational Guide: Generating CycloneDX SBOMs for DSL Analysis

This guide documents the complete and standardized procedure for generating **Software Bill of Materials (SBOM)** documents compliant with the **OWASP CycloneDX** specification (v1.4 - v1.6+) from real-world software projects, and preparing them for analysis with the `sbom-dsl` compiler.

---

## 1. Real-World DevSecOps Pipeline Flow

In modern software engineering, an SBOM is never written manually. The industry pipeline follows four sequential stages:

```
[ Source Code / Project Manifest ] (e.g. package.json, pom.xml)
                 ↓
[ 1. Dependency Resolution ]        (e.g. package-lock.json - resolves transitive graph)
                 ↓
[ 2. CycloneDX Generator ]          (emits inventory and direct/transitive dependency graph)
                 ↓
[ 3. Vulnerability Scanner ]        (enriches SBOM with CVE advisories and CVSS scores - VEX)
                 ↓
[ 4. sbom-dsl (This Compiler) ]     (evaluates queries, calculates blast radius, enforces CI/CD gate)
```

## 2. Generating an SBOM for a Node.js Backend Microservice

This is the exact operational procedure used to construct the primary benchmark fixture of our project.

### Step 2.1: Directory Setup and Service Manifest
Create a dedicated working directory:
```bash
mkdir my-service && cd my-service
```

Create the `package.json` manifest specifying the service dependencies:
```bash
cat << 'EOF' > package.json
{
  "name": "payment-service",
  "version": "1.2.0",
  "description": "Cloud-Native Payment Microservice",
  "main": "server.js",
  "dependencies": {
    "express": "4.17.1",
    "jsonwebtoken": "8.5.1",
    "axios": "0.21.1",
    "qs": "6.7.0"
  }
}
EOF
```

> [!NOTE]
> When testing known security flaws, target versions with published advisories (e.g., `jsonwebtoken@8.5.1` contains the critical RCE flaw CVE-2022-23529; `qs@6.7.0` contains the prototype pollution flaw CVE-2022-29244).

### Step 2.2: Resolving the Transitive Dependency Graph
Execute `npm install` with the `--package-lock-only` flag:
```bash
npm install --package-lock-only
```
* **Mechanism:** It avoids downloading package tarballs to disk, but queries the official npm registry to generate `package-lock.json`, which resolves the exact hierarchical dependency tree of all 60+ transitive dependencies.

### Step 2.3: Emitting the Official CycloneDX Standard File
Run the official OWASP CycloneDX generator via `npx`:
```bash
npx -y @cyclonedx/cyclonedx-npm --output-file bom.json
```
* **Output:** A standardized `bom.json` conforming to CycloneDX v1.6 containing:
  - Root project metadata (`metadata.component`);
  - Complete software component inventory with purl identifiers, versions, and licenses (`components`);
  - Adjacency list of the entire dependency graph (`dependencies` with `ref` and `dependsOn`).

## 3. Generating SBOMs Across Other Ecosystems

The exact same workflow applies to other programming languages:

### Java (Maven)
Include the official plugin in `pom.xml`:
```xml
<plugin>
    <groupId>org.cyclonedx</groupId>
    <artifactId>cyclonedx-maven-plugin</artifactId>
    <version>2.7.11</version>
    <executions>
        <execution>
            <phase>package</phase>
            <goals><goal>makeAggregateBom</goal></goals>
        </execution>
    </executions>
</plugin>
```
Then execute:
```bash
mvn cyclonedx:makeAggregateBom
# Generated output located at: target/bom.json
```

### Python (pip / requirements.txt)
```bash
pip install cyclonedx-bom
cyclonedx-py requirements requirements.txt -o bom.json
```

### Docker Containers / Arbitrary Filesystems (Agnostic Tool: Syft)
Using Anchore **Syft**, a widespread enterprise open-source tool:
```bash
# Scan an arbitrary local project directory:
syft dir:/path/to/project -o cyclonedx-json=bom.json

# Scan a container image (e.g. Redis or Nginx):
syft docker:nginx:latest -o cyclonedx-json=nginx_bom.json
```

## 4. Enriching SBOMs with Vulnerability Catalogues (VEX Enrichment)

A raw SBOM generated by package managers catalogs components but does not embed vulnerability advisories by default. In industrial pipelines, security scanners perform this enrichment:

### Automated Enrichment with Trivy or Grype:
```bash
# Scans dependencies and outputs a vulnerability-enriched CycloneDX SBOM:
trivy fs . --format cyclonedx --output bom-with-vulns.json
```

### CycloneDX Vulnerability Schema Structure:
The resulting JSON populates the `"vulnerabilities"` array:
```json
"vulnerabilities": [
  {
    "id": "CVE-2022-23529",
    "description": "Remote Code Execution flaw in jsonwebtoken",
    "ratings": [
      {
        "source": { "name": "NVD" },
        "score": 9.8,
        "severity": "critical",
        "method": "CVSSv31"
      }
    ],
    "cwes": [94, 502],
    "affects": [
      {
        "ref": "pkg:npm/jsonwebtoken@8.5.1"
      }
    ]
  }
]
```
> [!IMPORTANT]
> The critical relational link is **`affects[].ref`**, which matches the exact **`bom-ref`** of the affected library within the `components` list.  
> Our C++ compiler executes the relational **`HashJoin`** (`FIND VULNERABLE LIBRARIES`) on this attribute.

## 5. Querying and Verifying with `sbom-dsl`

Once the `bom.json` file is generated, query it directly with our compiler execution engine:

```bash
# 1. Inventory distribution metrics (SQL-like)
./build/sbom-dsl -c "SELECT type, COUNT(*) FROM components GROUP BY type;" -b bom.json

# 2. Supply chain upstream reachability (Graph BFS)
./build/sbom-dsl -c "WHO USES 'qs' TRANSITIVE;" -b bom.json

# 3. Hierarchical dependency tree rendering
./build/sbom-dsl -c "SHOW TREE DEPTH 2;" -b bom.json --format tree

# 4. Export to styled visual diagram
./build/sbom-dsl -c "SHOW TREE DEPTH 2;" -b bom.json --format mermaid
```
